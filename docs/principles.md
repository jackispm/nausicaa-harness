# Design Principles

这些原则约束 Nausicaa 的设计和实现；它们不是宣传口号，任何新增机制都应说明违反哪条原则以及为什么值得。

## KISS

保持少量核心概念：目标、lane、事件、产物、消息、建议。优先选择能被日志和测试解释的简单机制，不提前引入 graph、daemon、数据库或自动规划框架。

## DIY

对决定 Nausicaa 差异的部分保持自主：lane 步长与预算、Ledger 事件模型、Teto ObservationPort、Fukai 的可选边界、A2A Advice 和上下文视图。对 provider、流式协议、TUI 渲染等成熟通用基础能力直接复用 `pi-ai` 和 `pi-tui`，不重复造轮子。

## 小内核、可替换边界

核心只负责事实、调度、查询、通信和策略。模型、工具、存储、执行环境、传输和 UI 都通过窄接口接入；任何单个实现都不应成为产品概念本身。

## 空上下文与高缓存命中

模型只接收完成当前决策所需的最小上下文。任何模型 lane 都不能直接扫描 Ledger、Store、主线 transcript 或完整索引；每条 lane 使用自己的窄 Context Contract。Fukai 只是可选的按需查询实现，Teto 默认只消费固定大小的 ObservationFrame。稳定的系统指令和 schema 固定在前缀，动态内容以增量和引用追加；大对象按需读取。

## 主线优先、辅助线克制

辅助线必须有独立预算、冷却、去重和过期时间。建议默认可延后或拒绝，不能把“更多思考”自动变成更多 token 或更多打断。

## 事实、假设、决定分离

Ledger 中的事实不可由摘要悄悄覆盖；辅助线产生的是带证据引用和置信度的假设；主线或用户才负责做决定。每个决定都应能回溯来源。

## 可验证优先

“更智能”“更像心流”都不是验收标准。用任务成功率、偏离纠正率、建议噪声、token 成本、缓存命中、延迟和恢复能力验证设计。

## 模型单调性

优先建设会随模型能力增强而增强的机制：独立 lane、选择性取证、显式通信、持久事实和可恢复协作。避免把弱模型时期的临时补偿固化进内核，例如冗长纠错 Prompt、手写推理流程、脆弱 planner 和试图替模型判断的启发式评分。

内核只保留模型自身无法提供的结构性能力：并行隔离、持久事实、权限、通信、观察帧和恢复。Prompt 与 lane policy 必须短小、可版本化、可替换；模型升级时应允许删除补偿规则，而不改动 Ledger、ObservationPort 或 A2A 契约。

“多 lane 相对单 loop 的收益会随模型增强”是 Nausicaa 的核心实验假设，不是未经测试的事实。每个模型层级都必须比较 Main-only 与 Main+Teto；如果增强模型不能提高 Advice 质量或净收益，就要简化机制。

## 渐进复杂度

先用单进程、文件或内存实现验证协议，再决定是否需要数据库、远程运行、复杂调度、Fukai Execution 或 UI。没有实验结果，不把前卫概念固化成基础设施。Teto 先用 ObservationFrame 和 A2A 问答验证，不提前把 Fukai 查询或持久 REPL 变成必需依赖。

## 代码预算

MVP 自有生产 TypeScript 目标为 3,200-4,800 行；超过 6,000 行必须暂停扩展并审查边界。本地可用 v1 目标为 6,000-9,000 行。测试不计入该预算，也不能为压缩行数牺牲可读性。首期保持单 package、单进程、固定 Main+Teto 拓扑。
